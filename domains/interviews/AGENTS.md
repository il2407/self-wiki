# Interview Domain Protocol

These instructions extend the repository-level `AGENTS.md` for interview work.

## Objective

Improve the user's ability to solve, explain, and reason in backend interviews.
The goal is demonstrated interview performance, not merely polished notes.

## Classify before practice

Use exactly one primary mode:

- `coding`: solve or review code under interview constraints.
- `system-design`: design a system and defend trade-offs.
- `technical`: explain a backend concept precisely.
- `project`: reconstruct and explain the user's actual experience.
- `behavioral`: communicate a real experience as a structured story.
- `job-fit`: map evidence to a specific role and company.

Do not apply a coding-question rubric to a project discussion, and do not treat a
project recollection as an externally sourced technical fact.

## Coding mode

1. Present only the problem, examples, and constraints.
2. Ask the user to clarify and propose an approach before coding.
3. Do not give hints until requested or the agreed timebox expires.
4. Evaluate correctness, complexity, edge cases, communication, and code quality.
5. Record mistakes by pattern, not only by problem name.

## System-design mode

1. Require requirements and scale clarification first.
2. Progress through API/data model, high-level design, bottlenecks, reliability,
   observability, and trade-offs.
3. Introduce new constraints incrementally.
4. Evaluate reasoning and communication, not resemblance to one canonical design.

## Technical mode

1. Ask for an explanation before supplying one.
2. Test boundaries with counterexamples and follow-up questions.
3. Separate memorized definitions from operational understanding.
4. Create or update a gap when the user cannot explain consequences or trade-offs.

## Project mode

1. Read the relevant page under `shared/projects/` first.
2. Treat raw evidence, recollection, inference, and interview phrasing separately.
3. Ask one question at a time when simulating an interviewer.
4. Probe ownership, architecture, decisions, scale, failures, alternatives, and
   what the user would change today.
5. Never invent a better historical rationale after the fact.

## Behavioral mode

Use real events only. STAR may structure a story, but do not fabricate stakes,
conflict, action, or impact. Keep a natural short version and a detailed version.

## Job-fit mode

Link every claimed match to evidence in the resume, a shared project, or a skill
page. Mark unsupported requirements as gaps, not strengths.

## Mock interview output

Every completed mock interview records:

- setup and timebox
- questions asked
- the user's answers or faithful summaries
- strengths with evidence
- gaps and mistakes
- improved answer outlines
- follow-up drills
- next review date

Do not overwrite a prior mock interview; create a new dated session.
